### 1.4 当前核心 Bug / 技术债

1. **node:sqlite 风险**：`server/db.ts` 使用 `node:sqlite`（Node 22.5+ 实验性 API），社区生态几乎为零，任何主流 ORM（Drizzle/Prisma）均不支持，API 可能在后续 Node 版本变更。
2. **同步没有认证**：`POST /sync/push` 和 `GET /sync/pull` 完全无认证，局域网内任何人可读写数据。目前靠 Tailscale 网络隔离保护，一旦公网暴露即成漏洞。
3. **IndexedDB iOS 配额限制**：Safari/WKWebView 的 IndexedDB 存储配额约为设备空间的 20%，超出后系统可能清除，无任何告警机制。
4. **同步调试用 `window.__lastSyncError`**：`sync/engine.ts` 中遗留 `(window as any).__lastSyncError = String(e)` 调试代码，应清理。

## 二、竞品调研

### 2.1 Anki（对标基准）

**优势**：
- FSRS-5 + 个人参数优化（基于用户历史，每月优化一次）
- 数万个社区共享牌组（AnkiWeb）
- 丰富卡片类型：Basic、Cloze、Image Occlusion、Multiple Choice
- Cloze + TTS 组合是语言学习标配
- `.apkg` 生态：几乎所有学习社区的标准格式

**劣势**：
- 界面是 2000 年代风格，学习曲线陡峭
- 移动端（AnkiMobile）收费 $24.99
- 设置项过多，新用户困惑

**FlashMind 对比定位**：FlashMind 的 UI 和移动体验显著优于 Anki，但功能广度差距很大。目标是"现代化的 Anki，UI 更好，功能聚焦核心"。

### 2.2 RemNote

**核心差异化**：笔记即卡片，知识库与复习系统一体化。
- 支持 Basic、Cloze、Image Occlusion、Multiple Choice
- Readwise 直接同步高亮为卡片
- 从手写笔记生成卡片（图片识别）
- 层级标签系统（rem hierarchy）

**FlashMind 学习点**：
- **从文本直接创建卡片**（`::` 语法）的摩擦极低
- **Readwise 集成**——用户在阅读中产生的高亮，自动变成复习卡片，这解决了"内容从哪来"的问题

### 2.3 Mochi Cards

**核心差异化**：Markdown-native，支持 cloze 和图片遮挡，TTS 朗读，Local-first。
- 无服务器版本（本地 SQLite），与 FlashMind 架构最接近
- 内置 TTS（卡片翻转后自动朗读）
- 支持从 Anki 导入 `.apkg`
- 官网明确写 "Hear your cards spoken aloud for better pronunciation"

**FlashMind 学习点**：TTS 朗读是语言学习用户的刚需，且 Mochi 已验证这个功能有市场。FlashMind 的 `tts_cache` 表表明这个功能已规划但未实现。

### 2.4 Obsidian + spaced-repetition 插件生态

**核心差异化**：知识库与复习深度集成。
- `obsidian-spaced-repetition`：已支持 FSRS（2024 年升级）
- `RecallFlow AI`（2026年5月）：AI 生成 FSRS 卡片，直接从 Obsidian vault
- `Decks plugin`：FSRS 卡片系统，迁移工具

**市场信号**：Obsidian 社区有大量用户在探索 FSRS + 笔记集成。这说明"从已有内容生成卡片"是真实痛点，AI 生成方向完全正确。

### 2.5 AI 生成卡片的新趋势（2024-2026）

- **StudyClock、AskSia、Vaia** 等新产品主打"上传材料，AI 自动生成卡片"
- arxiv 2026 论文《Memdora》研究 AI-Powered 闪卡交互，提出超越二元翻牌的评分模式
- **GPT-4 生成卡片质量**：已有研究（Gossmann, 2024）实测 GPT-4 生成卡片质量 > GPT-3.5，但都不如人工精心制作的卡片——这意味着 AI 生成需要用户确认环节

## 三、FSRS 算法深度分析

### 3.1 现有实现的限制

`src/algorithm/fsrs.ts` 中：
```typescript
const params = generatorParameters()  // 使用全局默认参数
const scheduler = fsrs(params)
```

这意味着所有用户使用相同的记忆模型参数，没有针对个体记忆特征的优化。

### 3.2 个人参数优化的价值与代价

**价值**：
- FSRS 官方数据：在 20,483,712 条 Anki 真实复习数据上，FSRS log-loss = 0.35 vs SM-2 的 0.45，改进 22%（[来源](https://github.com/ammmcreativetech-dot/quanta-fsrs)）
- 个人参数优化后可进一步降低约 20-30% 复习量（Anki FSRS 官方文档）
- Anki 建议：复习次数 ≥ 1000 次后优化，之后每月或每次复习量翻倍时再优化

**代价**：
- `fsrs-optimizer` 是 Python 包，Node 后端需要 fork 子进程或 API 调用
- 用户复习不足 1000 次时，优化出的参数比默认参数还差
- **结论**：优先级低，等用户积累足够数据再做。收益对小数据集用户微乎其微。

### 3.3 Cloze 删除的认知价值（已有文献支持）

clozemaster.com 博客（2026年发布）引用研究：句子语境中学习的词汇比孤立记忆保留时间更长，迁移到实际使用效果更好。具体数字：cloze 删除在长期词汇保留和实际使用上均优于传统正反面卡片。

**代码现状**：`ClozeSegment` 类型定义已存在于 `src/types/index.ts`，定义了 `type: 'text' | 'blank'`、`text`、`index` 字段，30% 基础已有。

## 五、分项深度优化方案

### 5.1 P0：Cloze 完形填空（代码最近，价值最高）

**现状**：`ClozeSegment` 接口和 `card_type?: 'basic' | 'cloze'` 已在类型系统中，但 UI/逻辑层完全未使用。

**实现路径**：

1. **编辑器**：在 CardEditor 添加 `{{c1::被遮挡的词}}` 语法支持
   - 工具栏按钮"添加填空"，选中文字后自动包裹 `{{c1::...}}`
   - 正面显示：将 blank 替换为 `___` 占位符
   - 背面显示：依次揭示每个 blank

2. **复习流程变化**：
   - 有多个 cloze 的卡片：每次复习只揭示一个 blank（当前最难的那个，按 FSRS 难度排序）
   - 打分逻辑不变

3. **数据库**：`card_type` 字段已在 schema 中（需确认 SQLite 侧也有该列）

**工作量估算**：编辑器 1 天，渲染层 1 天，复习逻辑 1 天，测试 1 天，共 4 天。

---

### 5.2 P0：Anki 导入（.apkg 格式）

**格式解析**：`.apkg` 是 ZIP 文件，内含 `collection.anki21`（SQLite）和媒体文件。

**MVP 限制范围**（控制工作量）：
- 只支持 Basic 和 Cloze 类型的文本卡
- 跳过媒体文件（图片/音频）
- 跳过调度数据（全部重置为 New 状态，让 FSRS 重新调度）

**实现路径**：
```
前端：
  1. 选择 .apkg 文件
  2. JSZip 解压（jszip 包）
  3. sql.js 读取 SQLite（WebAssembly）
  4. 解析 notes 表：提取 flds 字段（`\x1f` 分隔的正反面）
  5. 解析 cards 表：获取 deck 归属
  6. 显示预览（N 个 deck，M 张卡片）→ 用户确认
  7. bulkImportCards 写入 Dexie
```

**依赖**：`jszip`（现有）+ `sql.js`（新增，30KB WebAssembly）

**工作量估算**：3-5 天（含测试）

---

### 5.3 P1：AI 辅助生成卡片（最小版）

**MVP 设计**：
1. CardEditor 页面新增「AI 生成」入口
2. 弹出文本输入框（粘贴文本，最大 2000 字）
3. 调用 LLM API（用户自行配置 API Key，支持 OpenAI/本地 Ollama）
4. 返回 JSON 格式的卡片列表：`[{front, back, tags}]`
5. 卡片预览页：用户可编辑/删除每张卡片
6. 确认后批量导入

**Prompt 设计原则**（来自学术研究）：
- 要求生成原子化卡片（一卡一知识点）
- 避免过长的背面
- 优先 cloze 格式用于语言材料
- 要求 JSON 结构化输出

**API Key 存储**：LocalStorage 加密存储（或用户每次手动输入，不持久化）

**工作量估算**：4-6 天

### 5.4 P1：node:sqlite → better-sqlite3 迁移

**当前风险证据**：
- `server/db.ts` 使用 `import { DatabaseSync } from 'node:sqlite'`
- 这是 Node 22.5 引入的实验性 API，API 不稳定
- 无法使用 Drizzle、Prisma 等 ORM 减少样板代码
- `// @ts-ignore` 注释已说明类型不完善

**迁移步骤**：
1. `server/package.json` 添加 `better-sqlite3`
2. `server/db.ts`：将 `new DatabaseSync(path)` 替换为 `new Database(path)`
3. API 几乎一致（`db.exec`, `db.prepare`, `stmt.run`, `stmt.all`, `stmt.get`）
4. 移除 `// @ts-ignore`，添加 `@types/better-sqlite3`

**工作量**：半天（1 小时迁移 + 测试）

---

### 5.5 P1：同步认证（JWT Token）

**当前漏洞**：`POST /sync/push` 任何人都可调用。Tailscale 提供网络层隔离，但这不是安全保证，是依赖外部环境的侥幸。

**最小认证方案**：
```
服务端：生成一个 SECRET_TOKEN（启动时从环境变量读取）
         POST /sync/push / GET /sync/pull 检查 Authorization: Bearer <token>
客户端：设置页新增「同步密钥」输入框，存 localStorage
         每次请求带 Authorization header
```

无需 JWT 库，简单的 Bearer token 就够一人使用场景。

**工作量**：2-3 小时

---

### 5.6 P1：遗忘曲线可视化

**数学基础**（FSRS 公式）：
```
R(t) = 0.9^(t/S)
```
其中 `R` 是保留率，`t` 是距上次复习的天数，`S` 是稳定性（已存储在每张卡片上）。

**UI 设计**：
- 在牌组详情页的卡片列表行，点击卡片展开详情
- 展示一条曲线：x 轴 = 未来天数（0-60天），y 轴 = 保留率（0-100%）
- 标注"预计遗忘点"（R = 70% 时）
- 用 recharts `LineChart`，数据全部从 IndexedDB 计算，无需后端

**工作量**：2 天

### 5.7 P2：TTS 语音朗读

**现状确认**：`server/db.ts` 中 `tts_cache` 表已建，但路由实现状态需检查。

**实现方案**：
1. 卡片背面翻转时，自动调用 TTS 接口朗读正面或背面文字
2. TTS 来源（可配置）：
   - 浏览器原生 `SpeechSynthesis API`（免费，无需后端，质量一般）
   - Edge TTS（微软，质量好，通过 `edge-tts` 包在后端调用）
   - 缓存结果到 `tts_cache` 表，避免重复请求
3. 复习页新增设置：「翻牌后自动朗读」开关

**工作量**：先做浏览器 SpeechSynthesis 版本（半天），后接 Edge TTS（2 天）

---

### 5.8 P2：推送通知（学习提醒）

**技术约束**（实测数据）：
- Web Push API 在 iOS Safari 16.4+ 才支持（2023年4月）
- 需要 HTTPS（Tailscale 内网 + 自签证书可绕过，但配置麻烦）
- 需要用户主动授权

**实现路径**：
1. Settings 页：「每日提醒时间」选择器
2. Service Worker 注册 Web Push
3. 服务端发送 Push 消息（需 `web-push` npm 包 + VAPID 密钥）
4. 通知内容：「今日有 N 张卡片待复习」

**工作量**：3-4 天（含 HTTPS 配置文档）

---

### 5.9 P2：模糊答案验证（打字作答模式）

**背景**：现有模式是"翻牌 + 自评"，适合碎片化复习。打字作答模式对主动回忆要求更高，适合需要准确记忆的场景（外语拼写、公式等）。

**设计**：
- 卡片可设置 `answer_mode: 'flip' | 'type'`（默认 flip）
- `type` 模式：显示正面，用户输入答案，提交后对比
- 对比算法：`Levenshtein distance`，容错率可配置（≤2个字符差视为正确）
- 不需要 LLM，本地计算即可

**工作量**：3 天

## 六、产品层面的更高维度思考

### 6.1 内容来源是最大的增长瓶颈

研究发现（多个来源确认）：用户放弃闪卡 App 的最主要原因是**内容制作成本太高**。每张卡片都要手动输入正反面，门槛极高。

**FlashMind 目前的解法**：只有 CSV 导入。
**竞品的解法**：AI 生成（StudyClock）、高亮即卡片（Readwise/RemNote）、从笔记自动提取（Obsidian 插件）。

**建议路径**：
1. 短期：AI 从文本生成（P1）
2. 中期：Readwise API 集成（从阅读高亮自动创建卡片）
3. 长期：浏览器扩展（划词即加卡）

### 6.2 gamification 是留存的关键，不是装饰

研究数据（来源：elearningindustry.com）：间隔重复 + 游戏化组合比单独使用任何一种方法留存率高 3 倍。Duolingo 数据：streak + 游戏化使 Day-7 留存提升 14%。

**FlashMind 现有的游戏化**：连续天数 streak（🔥）。

**可以低成本添加的**：
- **成就徽章**：首次复习 100 张、连续 7 天、掌握第一个牌组
- **里程碑庆祝**（已有完成页庆祝动画，扩展即可）
- **每周回顾**：周日显示本周复习量、与上周对比、最强牌组

**注意**：过度游戏化会反效果（yukaichou.com 研究：infinite streak 会产生焦虑）。建议保持克制，不要做排行榜。

### 6.3 Anki 生态兼容性是获客的最短路径

Anki 社区 AnkiWeb 有数万个高质量共享牌组，几乎覆盖所有学习领域（医学、语言、历史、编程等）。`.apkg` 导入是接入这个生态的钥匙。

一旦 FlashMind 支持 `.apkg` 导入，用户不需要从头制作卡片——直接下载 Anki 社区的现成牌组，迁移成本降到最低。

### 6.4 同步架构的演进路径

**现在**：手动服务器 + Tailscale（适合个人/少数设备）
**下一步**：Bearer Token 认证（P1，解决安全问题）
**未来**：
- 选项 A：Turso（LibSQL，分布式 SQLite）替换 SQLite，天然支持多区域
- 选项 B：用 Electric SQL 实现 CRDT-based 同步（比自研 CRDT 成本低得多）
- 选项 C：Cloudflare Workers + D1（Cloudflare 的边缘 SQLite，免费额度够个人使用）

| 同步 Bearer Token 认证 | 0.5天 | 安全漏洞，当前靠 Tailscale 侥幸保护 |
| Cloze 完形填空（MVP） | 4天 | 代码 30% 已有，最大价值/成本比 |
| 清理调试代码（`__lastSyncError`） | 0.5小时 | 规范性 |

### Phase 2（2-3 周，增长）

| 任务 | 工作量 | 优先原因 |
|-----|-------|---------|
| Anki .apkg 导入（仅文本卡） | 5天 | 打通 Anki 生态，获客最短路径 |
| 遗忘曲线可视化 | 2天 | 零后端成本，显著提升产品专业感 |
| AI 生成卡片（文本输入版） | 5天 | 解决内容制作摩擦点 |

### Phase 3（1月+，深化）

| 任务 | 工作量 | 说明 |
|-----|-------|------|
| TTS 语音朗读 | 2-3天 | 语言学习场景标配 |
| 成就系统（徽章） | 3天 | 低成本游戏化，提升留存 |
| 模糊答案验证（打字模式） | 3天 | 主动回忆强化 |
| 推送通知 | 4天 | 需 HTTPS 配置 |

### 明确不做的功能

- **CRDT 冲突解决**：last-write-wins 解决的是真实场景，CRDT 解决的是极低概率的假问题
- **知识图谱/双向链接**：产品定位漂移，不是闪卡 App 的核心
- **渐进式阅读**：工作量极大，真实用户极少
- **牌组社区共享**：运营问题优先于技术实现，没用户的社区是鬼城
- **Capacitor 原生 App**：PWA + Tailscale 方案已够用，App Store 审核流程负担过重
- **FSRS 个人参数优化**：数据积累不足 1000 次之前有害而非有益
